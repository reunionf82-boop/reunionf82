# 운영자 안내 매뉴얼: 결제 완료되었으나 pending으로 남은 경우 (재시도하기)

## 1. 이 케이스가 발생하는 경우

- **상황:** 고객이 결제를 완료했는데, 시스템에 결제 상태가 **pending**으로만 남아 있어 점사를 진행하지 못한 경우
- **원인 예:** 결제 성공 페이지 로드 직후 창을 닫음, 네트워크 오류로 결제 완료 처리(complete)가 서버에 반영되지 않음 등
- **DB에서 확인:** Supabase **payments** 테이블에서 해당 고객(휴대폰/이름) 조회 시 **status = 'pending'** 으로 보이고, PG/결제사에서는 실제 결제 완료로 확인되는 경우

---

## 2. 운영자 처리 절차

### 2-1. 결제 완료 여부 확인

1. Supabase **payments** 테이블에서 고객 휴대폰번호 또는 이름으로 검색
2. **status**가 **pending** 인 건 확인
3. 결제사(PG) 또는 입금/승인 내역으로 **실제 결제 완료** 여부 확인
4. **실제로 결제가 완료된 건만** 아래 절차 진행 (미결제 건은 재시도 비밀번호 안내하지 않음)

### 2-2. ⚠️ 반드시 실서비스(프로덕션)에서만 진행

- **재시도하기·3203 확인은 실서비스(프로덕션) URL에서만 하세요.** 개발/스테이징 서버에서 하면 그 기록은 해당 DB에만 있어서, 고객이 실서비스에서 재시도할 때 **「복구 가능한 기록이 없습니다」** 가 나옵니다.
- 고객에게 안내할 **폼 주소는 실서비스(프로덕션) 주소**로만 안내하고, 운영자가 3203으로 확인할 때도 **실서비스 페이지**에서 진행해야 고객이 점사보기까지 성공할 수 있습니다.

**실서버에서 고객이 성공하려면 (개발에서 테스트한 경우)**

- 개발 서버에서 김동관 전화번호 + 3203으로 확인해 보셨다면, 그 결과는 **개발 DB**에만 반영됩니다. 실서버(프로덕션)에는 영향이 없습니다.
- **고객(김동관)이 실서버에서 성공하려면:** 실서버 **payments** 테이블에 해당 고객 전화번호로 된 **status='pending'** 건이 있어야 합니다. (실제 고객이 실서비스에서 결제했을 때 생긴 건이면 이미 있습니다.)
- **절차:** 고객에게 **실서비스 폼 주소**만 안내한 뒤, 고객이 실서비스에서 **재시도하기 → 본인 전화번호 + 3203 → 재시도하기** 를 하면 됩니다. 3203은 **user_credentials 없이** 실서버 payments의 pending 건만 찾아서 success로 바꾸므로, 실서버 DB에 해당 전화번호의 pending 건만 있으면 성공합니다.
- 실서버 payments에 해당 고객 pending 건이 없다면(예: 결제가 실서비스가 아닌 다른 환경에서만 발생한 경우) 「확인된 pending 결제가 없습니다」가 나옵니다. 이때는 실서버 payments에 해당 건이 있는지, 전화번호 형식이 일치하는지 확인하세요.

### 2-3. 고객 안내 (재시도하기 + 비밀번호 3203)

고객에게 아래 내용을 **문자/전화/메일** 등으로 전달합니다. **(안내할 URL은 반드시 실서비스 주소입니다.)**

---

#### 【고객 안내 문장 - 기본】

```
결제는 정상적으로 완료된 것으로 확인되었습니다.
아래 방법으로 다시 접속하시면 점사(결과)를 진행하실 수 있습니다.

[이용 방법]
1. 재유니온(재회) **실서비스** 폼 페이지로 접속 (안내해 드린 주소 사용)
2. 결제하셨던 상품 선택 후, 결제 정보 입력란 아래 "이미 결제하셨나요? 재시도하기" 클릭
3. 휴대폰 번호: (고객 본인 번호)
4. 비밀번호: 3203
5. "재시도하기" 버튼 클릭
6. 이동된 화면에서 상기 본인정보를 확인(필요시 수정)한 뒤, "점사보기" 버튼을 눌러 점사를 시작해 주세요.
7. 점사 완료 후 나의 이용내역에서 다시 보기 시, 휴대폰 번호 + 비밀번호 3203 으로 로그인하시면 됩니다.

※ 결제 확인 후 24시간 이내에 점사보기를 눌러 주셔야 합니다.
※ 문의 사항이 있으시면 고객센터로 연락 부탁 드립니다.
```

---

#### 【고객 안내 문장 - 짧은 버전】

```
결제 완료 확인되었습니다. 서비스 폼에서 "이미 결제하셨나요? 재시도하기" → 휴대폰 번호 입력 후 비밀번호 3203 입력 → 재시도하기 클릭 → 이동된 화면에서 "점사보기" 클릭해 점사 진행해 주세요. (24시간 이내) 다시 보기는 나의 이용내역에서 휴대폰 번호 + 3203 으로 조회 가능합니다.
```

### 2-4. 운영자 주의 사항 (3203 비밀번호)

- **3203** 은 **pending 결제를 '결제 완료'로 인정할 때 쓰는 운영용 비밀번호**입니다.
- **나의 이용내역** 조회 시에는 **휴대폰 번호 + 비밀번호** 둘 다 일치해야만 해당 고객의 결과가 표시됩니다.
- 따라서 3203을 고객에게 알려줘도, **다른 고객의 이용내역은 보이지 않으며**, 각 고객은 **본인 휴대폰 번호 + 3203**으로만 자기 결과를 볼 수 있습니다.
- 3203은 **실제 결제가 완료된 고객에게만** 안내하고, 필요 시 주기적으로 변경(환경 변수 `PENDING_CONFIRM_PASSWORD`)을 검토하세요.

| 점사보기 클릭 시 만료 | 24시간 초과 후 점사보기 클릭 | `결제 확인 후 24시간이 지나 이용 기간이 만료되었습니다. 고객센터로 문의해 주세요.` |

## 4. 상황별 대응 요약

| 상황 | 운영자 확인 사항 | 고객 안내 요약 |
|------|------------------|----------------|
| 결제 완료됐는데 점사 못 함 | payments에서 해당 건 status=pending, PG/입금 확인 | 재시도하기 + 휴대폰 번호 + 3203, 24시간 이내 점사보기 |
| 24시간 지나서 만료됨 | completed_at 기준 24시간 경과 여부 | **어드민 → 재시도 예외 허용**에서 해당 주문번호(oid) 입력 후 허용. 고객에게 동일한 재시도 절차(휴대폰+3203 → 점사보기) 안내 |
| 재시도 시 "일치하는 정보가 없습니다" / "복구 가능한 기록이 없습니다" | 휴대폰 번호 오타, pending 건 존재 여부, 비밀번호 3203 확인, **실서비스 URL에서 시도했는지** 확인 | 휴대폰 번호·3203 정확히 입력, **실서비스(프로덕션)** 폼에서만 재시도. (개발 서버에서 3203 확인한 적 있으면 프로덕션 DB에 기록이 없어 실패함 → 실서비스 URL에서 다시 재시도하도록 안내) |
| 나의 이용내역에서 안 보임 | 해당 고객이 점사보기까지 완료했는지, 휴대폰+3203으로 조회했는지 | 점사 완료 후 나의 이용내역에서 휴대폰 번호 + 3203 입력 |

## 5. 기술 참고 (운영자/개발자용)

- **재시도 시 인증 경로**
  - **본인 비밀번호:** 결제 시점에 저장된 본인정보(pending_oid)로 재시도 → 본인 확인 후 success 전환 → 폼 이동
  - **3203:** 본인정보 없어도 휴대폰 번호 + 3203으로 pending → success 전환 후 폼 이동
- **24시간 기준:** payments 테이블의 **completed_at**(결제 확인 시각) 기준 24시간
- **환경 변수:** `PENDING_CONFIRM_PASSWORD` (기본값 3203) 로 재시도용 비밀번호 변경 가능

## 6. 24시간 경과 후 예외 허용 (어드민)

결제 확인 후 24시간이 지나 "이용 기간이 만료되었습니다"가 나온 고객을 **예외적으로** 점사보기 허용할 때 사용합니다.

### 6-1. 사전 준비 (최초 1회)

- Supabase SQL Editor에서 **`supabase-add-payment-retry-allowances.sql`** 실행하여 `payment_retry_allowances` 테이블 생성
- Security Advisor에 "RLS Disabled in Public" 오류가 보이면 **`supabase-enable-rls-payment-retry-allowances.sql`** 실행하여 RLS 활성화

### 6-2. 절차

1. 어드민 로그인 후 상단 **「재시도 예외 허용」** 버튼 클릭
2. **주문번호 (oid):** payments 테이블의 해당 건 `oid` 입력 (고객 결제 건의 주문번호)
3. **허용 시간 (시간):** 1~720 (기본 24시간, 최대 30일) 입력
4. **「허용」** 클릭
5. 고객에게 안내: **동일한 재시도 절차** (폼 → 이미 결제하셨나요? 재시도하기 → 휴대폰 + 3203 → 재시도하기 → 점사보기) 를 다시 진행하라고 전달

### 6-3. 표시 문장

- 예외 허용 후 고객이 해당 폼(confirmedOid 있는 URL)에 접속하면, 24시간이 지났어도 **만료 메시지 없이** 「점사보기」 버튼이 활성화되어 점사를 진행할 수 있습니다.

### 6-4. 예외 허용했는데도 프론트에서 "만료되었습니다"가 나올 때

어드민에서 해당 oid로 24시간(또는 N시간) 허용했는데, 고객 화면에서는 여전히 "결제 확인 후 24시간이 지나 이용 기간이 만료되었습니다"가 나오는 경우 아래를 순서대로 확인하세요.

1. **브라우저 캐시**  
   - 이전에 만료 응답이 캐시돼 있을 수 있습니다. **강력 새로고침**(Ctrl+Shift+R 또는 Cmd+Shift+R) 후 다시 시도하거나, 시크릿/프라이빗 창에서 같은 URL로 접속해 보세요.  
   - (개발 측에서 `/api/payment/status` 호출에 캐시 방지 적용이 되어 있어, 배포 반영 후에는 새로고침으로 해소되는 경우가 많습니다.)

2. **같은 환경(DB)인지 확인**  
   - 어드민을 **로컬/스테이징**에서 열고 허용한 경우, 그 DB에만 허용이 저장됩니다.  
   - 고객이 접속하는 **실서비스(프로덕션)** 는 다른 Supabase 프로젝트라면, 프로덕션 DB에는 허용이 없으므로 만료로 보입니다.  
   - **실서비스 어드민**에서 같은 oid로 다시 「재시도 예외 허용」을 실행하세요.

3. **테이블 존재 여부 (프로덕션 DB)**  
   - `payment_retry_allowances` 테이블이 **프로덕션** Supabase에 생성되어 있어야 합니다.  
   - 개발 DB에만 테이블을 만들었다면, 실서비스 API는 해당 테이블을 조회하지 못해 허용이 적용되지 않습니다.  
   - Supabase SQL Editor에서 **실서비스 프로젝트**에 `supabase-add-payment-retry-allowances.sql` 를 실행했는지 확인하세요.

4. **oid 일치**  
   - 어드민에 입력한 주문번호(oid)와 고객이 접속한 URL의 `confirmedOid`(쿼리 파라미터)가 **완전히 동일**한지 확인하세요. (공백/대소문자 포함)
